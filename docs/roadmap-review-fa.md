# بازبینی رودمپ‌های UniDev و پیشنهاد یک‌دست‌سازی

تاریخ بررسی: ۲۰ اکتبر ۲۰۲۶. مبنای بررسی، داده‌های فعلی سایت و سه فایل فرانت‌اند است. این سند پیشنهاد اصلاح محتوایی است؛ محتوای سه مسیر قبلی در این تغییر بازنویسی نشده است.

## نتیجه

احساس وجود مشکل در رفرنس‌ها درست است، اما مشکل همهٔ منابع یکسان نیست: تعدادی لینک خراب‌اند، تعدادی مقصد خیلی عمومی دارند، بعضی عنوانشان با مقصد نمی‌خواند و بعضی برای شروع یادگیری مناسب نیستند. یکسان کردن تعداد مراحل یا منابع به‌تنهایی این مسئله را حل نمی‌کند. واحد مشترک بهتر، «یک توانایی قابل‌آزمایش» است.

## بررسی رفرنس‌های سه مسیر قبلی

۴۷ جایگاه منبع، شامل ۴۳ URL متفاوت، با درخواست GET و دنبال کردن تغییر مسیر بررسی شد. نتیجهٔ هر جایگاه: ۲۷ پاسخ ۲۰۰، سه پاسخ ۴۰۴، یک پاسخ ۴۰۳ و ۱۶ نتیجهٔ نامشخص شبکه. تکرار یک URL در چند جایگاه در این شمارش لحاظ شده است. جزئیات قابل بررسی در [resource-link-audit.json](resource-link-audit.json) ثبت شده است.

**محدودیت شواهد:** پاسخ ۲۰۰ فقط دسترسی به صفحه را نشان می‌دهد و کیفیت یا پوشش آموزشی را ثابت نمی‌کند. خطای شبکه، ۴۰۳ و ناتوانی ابزار در خواندن یوتیوب نیز به معنی حذف‌شدن محتوا نیست. ویدئوها به‌طور کامل تماشا نشده‌اند.

## ایرادهای محتوایی و تعادل هر مسیر

### Django

ترتیب کلی Python ← وب و ابزارها ← Django ← دیتابیس ← احراز هویت ← API مناسب است. مسئله، تراکم موضوعات در پایان و چند ادعای نادرست یا بی‌پشتوانه است.

- در نکتهٔ OOP نوشته شده «تمام Modelها و Viewها کلاس هستند». دربارهٔ View درست نیست؛ Django صراحتاً [View تابعی](https://docs.djangoproject.com/en/5.2/topics/http/views/) دارد. متن پیشنهادی: «مدل‌ها کلاس‌اند و Viewها می‌توانند تابعی یا کلاسی باشند؛ برای کار با Viewهای کلاسی، ارث‌بری و super را بشناس.»
- عبارت «۹۵٪ شرکت‌ها» و توصیه‌های قطعی دربارهٔ مصاحبه‌ها منبع ندارند. آن‌ها را به توضیح کاربرد API در معماری‌های جداگانه تبدیل کنیم.
- تست به مرحلهٔ ۷ و بخش تکمیلی موکول شده است. تست مدل، مجوز و API باید همراه همان قابلیت آغاز شود؛ [مستندات تست Django](https://docs.djangoproject.com/en/5.2/topics/testing/overview/) نقطهٔ شروع مستقیم دارد.
- Celery، Redis و SOLID برای ورود اولیه هم‌سطح CRUD، احراز هویت و تست نیستند. بخش‌های تکمیلی مستقل مناسب‌ترند.
- برای امنیت، تست و استقرار، تمرین و معیار پایان صریح کم است. مثال معیار: «کاربر A نتواند دادهٔ خصوصی کاربر B را بخواند و تست این رفتار شکست دسترسی را اثبات کند.»

### علم داده

پاک‌سازی، EDA، اعتبارسنجی و اشاره به Data Leakage نقاط قوت‌اند. مسیر فعلی، تحلیل داده، ML و شاخه‌های پیشرفتهٔ AI را در یک دنباله جا داده است.

- هدف شغلی را روشن کنیم: تحلیل‌گر داده می‌تواند پس از SQL، آمار و EDA پروژهٔ مستقل داشته باشد؛ لازم نیست ابتدا همهٔ مدل‌های ML یا RAG را بداند.
- مرحلهٔ ۲، NumPy، Pandas، پاک‌سازی و SQL پیشرفته را یک‌جا دارد؛ مرحلهٔ ریاضی فقط دو مبحث بسیار بزرگ دارد. تقسیم بر اساس خروجی عملی، تعادل بیشتری از برابرکردن تعداد عنوان‌ها ایجاد می‌کند.
- XGBoost، LightGBM و CatBoost به‌عنوان سه الزام هم‌زمان سنگین‌اند. ابتدا baseline، ارزیابی درست و یک روش boosting؛ بقیه تعمیق انتخابی.
- جملهٔ «Window Functions در ۱۰۰٪ مصاحبه‌ها» پشتوانه ندارد. به «در تحلیل داده کاربرد زیادی دارد؛ JOIN، aggregation و Window Function را در یک تمرین به کار ببر» تغییر کند.
- برای استقرار با Pickle/Joblib، خطر بارگذاری فایل ناشناس جا افتاده است. [مستندات scikit-learn](https://scikit-learn.org/stable/model_persistence.html) ریسک اجرای کد با روش‌های مبتنی بر pickle را توضیح می‌دهد.
- معیار پایان پیشنهادی: «تقسیم train/test را پیش از برازش preprocessing انجام بده، یک baseline بساز، معیار مناسب انتخاب کن و نتیجه را با محدودیت‌هایش توضیح بده.»

### لینوکس و Docker

این مسیر به‌عنوان «پایه‌های لینوکس و کانتینر برای برنامه‌نویس» ارزشمند است. سه مرحله برای معرفی کامل DevOps کافی نیست، و عنوان فعلی سایت نیز بهتر است همین دامنهٔ محدود را حفظ کند.

- بخش سیستم‌عامل از Race Condition و Deadlock شروع می‌شود، اما راه‌اندازی محیط تمرین و کار روزمرهٔ ترمینال روشن نیست. یک شروع ساده با محیط آزمایشی و فایل‌ها، یادگیری را عملی‌تر می‌کند.
- عنوان Bash دارد، ولی در مباحثش متغیر، شرط، حلقه، exit code و اسکریپت کوچک به‌روشنی دیده نمی‌شود. یا این‌ها را اضافه کنیم یا دامنهٔ عنوان را به خط فرمان محدود کنیم.
- Docker CLI، lifecycle کانتینر و عیب‌یابی شبکه پیش از Dockerfile و Compose به توضیح بیشتری نیاز دارند. [آموزش رسمی Docker](https://docs.docker.com/get-started/) مرجع مناسب برای تنظیم ترتیب است.
- اگر بعدها مسیر کامل DevOps خواستیم، شبکه، CI/CD، مشاهده‌پذیری، پشتیبان‌گیری و عملیات باید به یک مسیر مستقل تبدیل شوند؛ Kubernetes را بی‌مقدمه به این پایهٔ کوتاه نچسبانیم.
- معیار پایان پیشنهادی: «سرویس و دیتابیس را با Compose اجرا کن، داده پس از بازسازی کانتینر بماند و خطای اتصال را از log و تنظیمات شبکه پیدا کن.»

### فرانت‌اند

تفکیک هسته و تعمیق، پیش‌نیاز، معیار پایان، دسترس‌پذیری و تست تدریجی، ساختار قوی‌تری برای یادگیری مستقل فراهم می‌کند. همین الگو می‌تواند مبنای یک‌دست‌سازی شود. موارد نیازمند بهبود:

- فایل اصلی فقط سه رفرنس الهام‌بخش دارد؛ آن‌ها دورهٔ آموزشی هر ماژول نیستند. در پیاده‌سازی، هر سه حفظ شده و ۲۲ منبع مستقیم و رسمی به‌عنوان منابع **تکمیلی** اضافه شده‌اند. هر ۲۱ URL متفاوت این منابع پاسخ ۲۰۰ داد؛ این نتیجه جای بررسی کامل پوشش آموزشی را نمی‌گیرد. [گزارش دسترسی](frontend-resource-link-audit.json).
- TypeScript در بخشی از props کامپوننت‌ها صحبت می‌کند، درحالی‌که React پیش‌نیاز آن اعلام نشده است. پیشنهاد آموزشی: اصول TS بعد از JavaScript، سپس بخش props هم‌زمان با React.
- ماژول ۶ چند توانایی بزرگ دارد. درخت فعلی پنج شاخهٔ اصلی آن را حفظ می‌کند؛ در ویرایش بعدی می‌توان «داده»، «فرم» و «routing/auth» را زیرواحدهای مستقل با معیار پایان جدا کرد.
- امنیت اصلی در ماژول ۷ آمده، اما مدیریت توکن و مجوز در ماژول ۶ مطرح است. احتیاط‌های ذخیرهٔ توکن و تفاوت نمایش مجوز در UI با کنترل واقعی سرور باید همان‌جا آموزش داده شود.
- عبارت‌هایی مثل «بدون هیچ کمک» را معیار مطلق حرفه‌ای بودن نگیریم. توانایی توضیح، اشکال‌زدایی و تصمیم‌گیری مستقل مهم است؛ استفادهٔ آگاهانه از مستندات مجاز باشد.
- «صفر any»، «همیشه Zod» یا «همیشه Next.js» هدف آموزشی عمومی مناسبی نیستند. هدف بهتر: دادهٔ ورودی نامطمئن اعتبارسنجی شود، نوع‌ها خطا را پنهان نکنند و ابزار با مسئله تناسب داشته باشد. فایل Markdown نیز سبک‌کردن Next.js را در پروژهٔ نامرتبط مجاز دانسته است.
- مباحث تخصصیِ ماژول ۸ هدف و معیار پایان جدا ندارند. هنگام انتخاب یک تخصص، یک پروژه و معیار پایان مخصوص همان شاخه تعریف شود.
- سطوح سه کارت پروژه در سایت برای نمایش مشترک انتخاب شده‌اند؛ متن اصلی سه نوع پروژه پیشنهاد می‌کند و برایشان سطح سختی رسمی تعیین نکرده است. «مبتدی» روی داشبورد، به معنی مناسب‌بودن همهٔ قابلیت‌های آن برای روز اول نیست.

## قالب پیشنهادی مشترک

برای همهٔ مسیرها، یک واحد یادگیری این اجزا را داشته باشد:

1. **هدف:** یک توانایی روشن در یک یا دو جمله.
2. **پیش‌نیاز:** نام مهارت و لینک واحد مربوط؛ ترتیب نمایشی با وابستگی واقعی اشتباه نشود.
3. **هسته:** معمولاً ۳ تا ۶ گروه هم‌سطح. عنوان کوتاه در درخت، جزئیات و مثال در پنل. عدد، راهنماست؛ دلیلی برای حذف محتوا نیست.
4. **تعمیق انتخابی:** معمولاً صفر تا دو گروه؛ به‌همراه توضیح اینکه چه زمانی لازم می‌شوند.
5. **منابع:** یک مسیر شروع مشخص، یک تمرین و در صورت نیاز یک مرجع. اگر یک منبع دو نقش دارد، دوبار نمایش ندهیم. تعداد منابع را صرفاً برای زیبایی برابر نکنیم.
6. **تمرین:** یک خروجی کوچک که از مباحث همان واحد استفاده کند.
7. **معیار پایان:** دو یا سه رفتار قابل مشاهده، بدون وعدهٔ استخدام یا ساعت مطالعهٔ تضمینی.

برای هر منبع، جداگانه `kind`، `language`، `role`، `cost/access`، `level`، `version`، `checkedAt` و فصل موردنیاز ثبت شود. URL مستقیم لازم است. تاریخ بررسی دسترسی با تاریخ بازبینی محتوا فرق دارد. منابعی که ناشر اجازهٔ خواندن خودکار نمی‌دهد، بازبینی دستی می‌خواهند.

نمونهٔ متعادل برای «دریافت داده در فرانت‌اند»:

- هدف: دادهٔ یک API را با وضعیت‌های موفق و شکست نمایش بدهی.
- هسته: قرارداد پاسخ، fetch و خطای HTTP، loading/empty/error، لغو و تکرار درخواست، صفحه‌بندی.
- تعمیق: caching و optimistic update در پروژه‌ای که واقعاً نیاز دارد.
- تمرین: فهرست قابل جست‌وجو با API و دکمهٔ تلاش دوباره.
- معیار پایان: خطای ۵۰۰ قابل بازیابی باشد؛ پاسخ خالی با خطا اشتباه نشود؛ دادهٔ ناقص رابط را خراب نکند.
- منبع شروع: [راهنمای Fetch در MDN](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)؛ مرجع تکمیلی: [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview).

## ترتیب اصلاح پیشنهادی

۱. ابتدا لینک‌های ۴۰۴، مقصدهای جستجو و عنوان‌های ناسازگار اصلاح شوند؛ ادعاهای درصدی و اشتباه «تمام Viewها کلاس‌اند» هم حذف یا تصحیح شوند.

۲. بعد برای هر بخش فعلی، پیش‌نیاز، تمرین و معیار پایان اضافه شود. موضوعات بزرگ بدون حذف به زیرواحد تبدیل شوند. شروع تست و امنیت به قابلیت مربوط نزدیک شود.

۳. در پایان لحن، برچسب منابع، سطح پروژه‌ها و تفکیک هسته/تعمیق در همهٔ مسیرها یکسان شود. هسته‌ها باید مستقل قابل تمرین باشند؛ یکسان‌بودن به معنی اجبار همه به تعداد مرحلهٔ برابر نیست.

## آنچه در این تغییر پیاده شد

- مسیر عمومی `/roadmaps/frontend` با پایه‌های وب و هشت ماژول؛ ۵۵ گرهٔ مبحث.
- محتوای اصلی هر ماژول، پیش‌نیاز، معیار پایان، تمرین‌ها و نقش AI؛ بخش‌های تعمیقی با برچسب اختیاری.
- راهنمای شروع، اصطلاح‌ها، مهارت‌های همراه، تنظیم مسیر، معیارهای آمادگیِ PDFها در بخش بازشوندهٔ راهنما. پرسش‌های خطاب به ویراستار در متن کاملِ قابل دریافت حفظ شده‌اند.
- سه رفرنس اصلی و ۲۲ منبع آموزشی تکمیلی با توضیح تفاوتشان.
- PDF فارسی، PDF انگلیسی و Markdown اصلی با همان محتوای فایل‌های ورودی و لینک دریافت.
- چیدمان درخت یک پیشنهاد نمایشی است؛ خط اتصال، ادعای پیش‌نیاز اجباری برای عبور از همهٔ ماژول‌ها نیست. پیش‌نیازهای واقعیِ ذکرشده در متن، در پنل با لینک ماژول مربوط نمایش داده می‌شوند.
- محتوای سه مسیر قبلی حفظ شده است؛ این گزارش مشخص می‌کند بازنویسی آموزشی بعدی چه تغییرهایی لازم دارد.


## شواهد بررسی پیاده‌سازی

- `npm run build`: موفق، شامل lint و بررسی TypeScript؛ مسیر فرانت‌اند در خروجی پیش‌ساخته‌شده ثبت شد.
- `node scripts/verify-roadmaps.mjs`: موفق؛ شناسه‌های یکتا، ساختار منابع، نبود چرخه در پیش‌نیازها و تطابق تمام فیلدهای ماژول‌های Markdown بررسی شدند.
- بررسی مرورگر روی نسخهٔ production محلی: تمام ۲۷ بخش چهار رودمپ، تعداد مباحث، عنوان‌ها، یادداشت‌ها، منابع و تمرین‌های موجود با داده‌ها مقایسه شد؛ خطای JavaScript مشاهده نشد.

- هر سه فایل دانلودی از سرور دریافت و با فایل ذخیره‌شده مقایسه شدند؛ فایل‌های ذخیره‌شده نیز با ورودی‌های اصلی یکسان‌اند.
- محتوای سه رودمپ قبلی با نسخهٔ پیش از افزودن فرانت‌اند مقایسهٔ کامل شد و تغییر نکرده است. امکانات ثبت تیک یا پیشرفت شخصی اضافه نشده‌اند.
